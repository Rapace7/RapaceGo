## ☐ P0-1 「推荐落点讲解」点一次就永久报废（必须重启软件）

- **位置**：`renderer/app.js:8208`（定义）、`:8328`（调用点）

- **根因**：
  ```js
  // :8208
  function pickPositionKey(at) {
    return JSON.stringify([N, settings.rules, settings.komi, state.setup, state.moves.slice(0, at)]);
  }
  ```
  `state.moves` 里装的是**树节点本身**（`:2123` / `:668` 造的节点带 `_p` / `_cs`）：子指父、父的 `_cs` 又含子 → **必然循环引用**，`JSON.stringify` 抛 `TypeError`。

  而调用点在 `try` **外**：
  ```js
  // :8327-8334

  const snapshot = { at, side, positionKey: pickPositionKey(at), gen: gameGen };  // ← 在这里抛
  state.coach.pickPending = snapshot;
  ```

  1. 序列化只取纯数据，例如

## ☐ P0-3 完全无视 SGF 的 `CA[]`：Big5 棋谱被当 GBK 读，**一编辑就永久写坏**

- **位置**：`main.js:1468`（`readTextSmart`）、`main.js:1506`（`writeTextSmart`）
- **证据**：✅已复核 + 🔬有实测（语料 `CA[]` 分布：无 CA 10185 / gb2312 2247 / **big5 1000**）
- **症状**：打开 `CA[big5]` 的棋谱 → 解说词/备注显示成"看着像中文的错字"；此时**改一处备注或解说词并保存** → Big5 原文被按 GBK 写回，**不可逆损坏**（只有 `.bak` 能捞，用户不会知道）。
- **根因**：
  ```js
  // main.js:1468
  function readTextSmart(p) {
    const buf = fs.readFileSync(p);
    if (looksUtf8(buf)) return buf.toString('utf8');
    try {
      const asGbk = new TextDecoder('gbk').decode(buf);
      if (asGbk.indexOf('\uFFFD') < 0) return asGbk;      // ← Big5 字节按 GBK 解
    } catch (e) { }
    return buf.toString('utf8');
  }
  ```
  只有"UTF-8 试探 → GBK 兜底"两条路，**`CA[]` 从头到尾没被读过**（全仓库 grep：`CA[` 只在 `app.js:2954` 作为**输出**出现）。
  **坑点**：Big5 字节按 GBK 解码**不产生 U+FFFD**（双字节区重叠），所以不是明显乱码，而是**合法的错字** → 走进 1473 返回错文本。
  `writeTextSmart:1508` 同样只判"原文件是不是 UTF-8"，否则一律按 GBK 写。
- **实测数据**（`00001_天龙图`）：
  - 按 big5 解：`博弈?棋教育网棋友?入，供大家??交流`
  - 应用看到的（GBK 解）：`痴?囱毙▅蔍囱ね?ㄑ產??ユ瑈`
  - 改一处说明落盘后：文件 209 → 167 字节，big5 侧原文变成 `扂樓賸珨曆佽隴`
  - 对照：未被编辑的中文属性值字节逐一相同 → 说明是"按位置改"，坏只坏在被编辑/被展示的那些字。
- **建议修法**：
  1. 解码前先从**字节**里嗅 `CA[xxx]`（值一定是 ASCII），命中 `big5` / `gb18030` / `gbk` / `gb2312` 时优先用对应 `TextDecoder`；
  2. **写回**也要按原编码。⚠️ Node 的 `TextEncoder` **不支持 big5** —— 要么参考 `gbkEncode`（`main.js:1480`）那套反查表另建一张，**要么在"写不回去"时拒绝落刀并如实提示**。
     **绝不能**继续"悄悄按 GBK 写回" —— 这正是本项目文档里最忌讳的事。
- **回归断言建议**：造一份 `CA[big5]` + 中文 `GN`/`C` 的棋谱 → 读出来断言中文**正确**；改一处 `C` 保存 → 按 big5 解回断言**可逆**（或断言工具拒绝落刀并给出提示）。
- **⚠️ 注意**：`gbkEncode` 用 `'?'`（0x3f）兜底"GBK 里没有的字"，本身是**有损**的；Big5 支持要一并考虑这个坑。

- **根因**：复用已有节点时**只 push 一个**，而别处的"换路径"走 `pathThrough`（沿 `_cs[0]` 铺到底）：

  ```js
  // :686 —— 别处的口径

    while (cur && cur._cs && cur._cs.length) { cur = cur._cs[0]; p.push(cur); } return p; }
  ```

## ☐ P2-1 `koPoint`（打劫禁着点）在**四个入口**分别丢失

> **这是本次审查里"重复出现次数最多"的一个病。四处独立成因，建议按最后给出的根治方案统一收口。**

- **证据**：✅已复核（`:215` / `:1145+1150` / `:5615` / `:2160` / `:2832`）+ 🔬有实测（两个子审查员**各自独立**发现，结论一致）
- **共性根因**：`koFromBoard`（`:2157`）第一句是
  ```js
  if (!last || last.pass || last.captured !== 1 || !last.capAt) return null;
  ```
  它**依赖 `captured`/`capAt` 两个派生字段**，而这两个字段只由 `rebuildCapAt()`（`:2180`）补，且 `rebuildCapAt` **只遍历 `state.moves`（当前路径）**。凡"换了路径但还没补字段"的时刻，`koPoint` 就算成 `null` → 非法提回被放行（违反规则）。

- **入口 ①  AI 停一手不清 `koPoint`** —— `app.js:5615`
  ```js
  if (pick === 'pass') {
    aiRetry = 0;
    pushPassNode();                   // ← 人类那条（:2849）这里还有一句 state.koPoint = null;
    state.viewAt = state.moves.length;
    syncUI();
  }
  ```
  人类停一手在 `:2852` 有 `state.koPoint = null;`（"脱先一手，劫自然消解"），**AI 这条漏了**。
  后果比子审查员描述的更广：`tryPlay:2069` 的拦截对**任何一方**都生效 —— AI 脱先后轮到人，人连**普通合法的一手**都不能落在那个点上，会被误报「打劫：不能立刻提回」。
  **修法**：补 `state.koPoint = null;`（与人类那条对齐）；更稳的是让 `pushPassNode()` 内部统一负责"脱先 → 劫消解"，避免第三个 pass 入口再漏。

- **入口 ②  切分支时重算次序反了** —— `app.js:1145` + `:1150`
  ```js
  setPath(full);        // :1145 → refreshDerived() → koFromBoard(...)  ← 此刻旁支节点还没有 captured/capAt → null
  ...
  rebuildCapAt();       // :1150 → 只补字段，**不重算 koPoint**
  ```

  ```js

  if (t === '(') {

    if (!sub) { k++; continue; }        // ← 空树 `()`：注释说"跳过"，实际是"把这棵树砍断"
    k = sub.next;
  }
  // :3125
  return first ? { node: first, next: k } : null;
  ```
  空树那次递归**内部已经把匹配的 `)` 也吃掉了**，调用方的补救 `k++` 于是正好落在那个 `)` 上 → 本层 `while` 的 `if (t === ')') { k++; break; }` 把**外层这棵树**收尾 → 后面全丢。
- **实测**：
  ```

  去掉 () 立刻是 5 个节点
  语料对照: 99/17290 不一致，其中 98 份含 ()  ←（另一 1 份是 ((，同一根因）
  ```
- **修法**：让 `parseTree` **永远返回 `{node, next}`**：
  ```js
  return { node: first, next: k };      // first 可为 null
  // 调用处：k = sub.next; if (sub.node && cur) cur.kids.push(sub.node);
  // 顶层：const r0 = head >= 0 ? parseTree(head) : null; const rootTn = r0 && r0.node ? r0 : null;
  ```
- **回归断言建议**：把子审查员的语料统计脚本改造成回归（17290 份 vs 参照实现，第一棵树的 B/W 节点数必须一致）—— 这条**跑一次就能覆盖整类 bug**。
