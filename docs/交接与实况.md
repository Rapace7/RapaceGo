## ★★★★★ 2026-10-15 凌晨 · **排序方向修正 + 插入让位加保险 + 真实棋谱回归**

> 首相看了图又报了两条（顺序不对、视野还在跳），并把新的诉求（分支路径绿色高亮）提上来了。
> **源码 = 免解压版（21:39 构建 / 21:40 zip）。**

### 一、首相报的两条

1. 「最新展开的根本就不会自动保持在最上层，**我最后展开的第一手居然跑到下面去了**」
2. 「有时候展开和收起会**自动跳到最后一手**，这个极其影响使用体验，**必须展开和收起时保持在当前视野**」
3. （看图二）「完全不会打到一起的两大坨分支竟然展开后放那么往下，简直一团乱麻了」

### 二、改了什么

**① 排序方向又翻了一次（这次有实测支撑）**

`all.sort` 的**方向**和"有没有插入让位"是**绑在一起**的，两个必须配套：

| 排序 | 插入让位 | 结果 |
|---|---|---|
| 倒序（后展开的先放） | 有 | **正确** —— 后展开的先占最靠上的空行，先展开的捡下面的 |
| 正序（先展开的先放） | 有 | 后展开的靠插入挤上去，但**插入会把先放好的顶下去** → 反而最后展开的在最下面 |
| 正序 | 无 | **正好反了** —— 先来先占，后来的往下排（实测 T12 直接挂） |

**定稿：倒序 + 有插入（带保险）**。
教训：**排序方向不能单独改** —— 它和"有没有插入"是一对，改一个必须同时想另一个。

**② 插入让位加了保险：只在"不会拉长任何已有的线"时才插**

插入 = 把 `row >= r` 的全部下移一行。于是"**父在 r 上方、子在 r 下方**"的那些斜线
**父端不动、子端下移** → 线被拉长 → 拉到后来**穿过中间行上的珠子**。

真实棋谱 181 手全部展开的实测（同一份数据，三个版本）：

| 版本 | 线穿珠子 | 行数 | 耗时 |
|---|---|---|---|
| 无插入（v8） | **9499 处** | 424 | 1.7 s |
| 有插入（v6/v9） | **10209 处** | 457 | 0.2 s |
| **有插入 + crossers 保险（定稿）** | **140 处** | **276** | 5.2 s |

`crossersAt(r)` 就一句话：数一数"父在 r 上方、子在 r 下方"的斜线有几条；
**只要大于 0 就不插**，改成往下找空位。
效果：平时按需展开（稀疏）照插，保住"后展开的挤上去"；点了「全部展开」（密集）不插，保住零接触。

**③ 视野跳走（首相报的②）**

根因在 `renderMoveTree`：判断"要不要自动把当前手滚进视野"的信号 sig **带了当前手所在的行号**，
而展开/收起**必然改变行号** → 每点一次角标都被当成"当前手换了" → 主动把视野拉过去。
**已修**：sig 只留 `clientWidth`（开关放大窗）、`recName`（换棋谱）、`viewAt`（当前手真的换了）。

### 二、算法定稿（`treeLayout` 第三版，v6）

**三条要求合成一个算法**：

- **放置顺序按"展开时间倒序"** → 最后展开的那条支**先挑行**，拿到最靠上的空行；
  先展开的随后挑，被挤到下面（要求①）。
  `treeExpanded` 旁边新增 `treeExpandSeq`（节点 → 展开序号），点角标 / 点全部展开时才发号。
- **找行从"父行的下一行"开始，只看 K=8 行** → 放得下就共用（要求②）。
- **K 行内都放不下 → 在父行正下方插一个空行，把它下面的全部推开**（要求③"自适应上下让位"）。
  **于是每条支的连线永远只跨一行**，不可能横穿别人的块。
  ⚠️ 这一条同时是**性能的关键**（见下）。

判据仍是三条几何检查（格子不重叠 / 入线不碰珠子 / 已放置的斜线不碰珠子），
每一条都能被断言直接验；`findRow` 有硬上界，判据再保守也只是多占一行，**不会卡死**。

### 三、★ 性能：16.4 秒 → 0.07 秒（**先量再改，一轮只改一个变量**）

真实打谱谱（181 手 / **457 条支** / **4720 颗珠子**）"全部展开"的实测：

| 版本 | 做法 | 耗时 |
|---|---|---|
| 第一版 | 逐行试到行尾 + 判碰时**全量扫**几百条斜线 | **16.4 秒** ❌ |
| 第二版 | 斜线按行分桶 + 链深列表只算一次 | 14.5 秒（只治了皮毛） |
| **第三版（定稿）** | **父行下面只看 8 行，放不下就插入一行** | **0.07 秒** ✓ |

### 一、首相的两条要求（原话）

1. 「如图一，全展开实在是太乱了，应该是**默认全部收起，按需展开**。」
2. 「如图二，分支里的分支会导致相交线……第二条支线里的 88 手后我开了一条支线，

   这条展开的话，按我的想法应该是**让最下面那条支线让道**，
   让出一行来给这条新的支线里的支线显示。」

### 二、改了什么

**① 折叠语义反转：`treeCollapsed` → `treeExpanded`**

- 旧的记"折起来的" → 默认空 = **全展开**；新的记"**展开的**" → 默认空 = **全收起**。
- 角标默认就是 `+n`（表示这一手后面有 n 条支），点开才变 `▾`。
- ⚠️ **当前显示那一手所在的路径必须自动展开**（`treeForceOpen`，每次 `treeLayout` 重算）——
  否则跳进某条支的第 5 手，那颗珠子根本不在树上（看着像"点了没反应"）。
  只标"侧支的**父节点**"，不是把整条祖先链都展开（否则又变回"太乱"）。
- 放大窗加了「全部展开 / 全部收起」两个按钮（默认收起后，"想一次看全"的开关）。
- **实测收益**：真实打谱谱 181 手（41 处分支）——
  **全展开要画 4720 颗珠子，默认收起只画 181 颗**（少 96%）。首相图一"一屏珠子"就是这么来的。

**② 行分配改「先序 DFS + 子树占连续行」（这就是"让道"）**

- 旧算法"每条侧支各自去找第一个列区间不冲突的行" → 父支在行 2，它的子支跟支 A/B/C 都撞
  → 只能落到**行 4**（比支 C 的行 3 还靠下）→ 连线从行 2 斜跨到行 4，**穿过支 C 那一行**
  ← 这正是首相看到的相交。
- 新算法：一条支占行 R，**它的子支落在 R+1**，且这条子支的整棵子树占 R+1 起的连续若干行；
  **排在后面的兄弟支，从"整棵子树用完之后"的第一行开始** —— 这就是"让道"。
- ⇒ 任何一条支的连线只从行 R 斜到**相邻行** R+1 → **数学上不可能穿过第三方珠子**，
  而且子支紧贴父支，一眼看得出谁是谁的分支。
- 代价：不再复用行，行数比旧算法多 —— 首相要的正是"让道"，配合默认收起不会失控。

**③ 一条旧断言口径作废（要记住）**

- 旧的 **T1b**「**任意**两个分叉，手数小的行号一定小」（10-13 定的）——
  跟新要求（子支紧贴父支 → 深层子支**必然**插到浅层兄弟支上面）**直接冲突**，已作废。
- 新口径：**同一父节点下的兄弟支**，靠前的排在靠上的行（那才是"顺序"该管的范围）。

  所以「175 的分支在最下、182 的分支在最上」，顺序正好反了；
- ② **两条在水平方向碰不到、下落线也不打架的支，可以共用一行** —— 原来每支独占一行，太浪费。

**已写进源码的做法**（`treeLayout` 第二次重写）：
- 阶段① 主变占第 0 行；阶段② `collect()` 收集所有侧支；阶段③ **按分叉手数 `depth0` 排序**后依次分配行；
- 复用一行的两条约束：**水平段从"父珠所在列"到本支末端整段要空** + **父列上从父行到本行每一格要空**；
- 顺手修掉一处：**虚拟根不该 `put` 进格**（原来会白占列 0、第 1 手的连线也少一截）。

**已知的可疑点（晚上优先看这三处）**：
1. `put()` 一口气写了 `treeCells` / `treePosOf` / `occ` / `treeLanes` / `treeMaxDepth` ——
   **任何一处抛异常都会让 `treeCells` 一个格子都没有**（表现正是"啥都没渲染"）；
2. `spanOf()` 的递归 与 `treeCollapsed` 的组合；
3. `branches.sort()` 之后，轮到某条支时 `rowOf(parent)` 是否**一定**已就绪（理论上 depth0 浅的先排，应该就绪，但要验）。

- ❌ 新算法**一次都没跑过**；❌ 没跑全量断言；
- ❌ **没构建 / 没同步 / 没覆盖 Release** —— **这是故意的**：坏的代码不能发出去。

**① 加判断函数** —— 放进 `renderer/app.js` 的「手数分支」那一节（搜 `function promoteToMainline`，放它前后都行）：

/* 当前走的是不是主变那条链（从根沿每层 _cs[0] 走到底）。

function currentPathIsMainline() {

### 【任务 2】🟡 手数列表显示「12a 式」手号（设计方案决策 6 · 约 30 分钟）

**要的效果**：

| 情形 | 显示 | 例子 |
|---|---|---|
| 这一手在**主变链**上 | 纯数字 = 从根数第几手 | `1` `2` `3` `4` `5` |
| 这一手在**旁支**上 | 数字（同样是「从根数第几手」）+ 岔口字母 | 主线第 3 手之后岔出的第 1 条支 → 它的第 4 手 `4a`、第 5 手 `5a` |
| 同一个岔口里的第 2 条旁支 | 字母换成 b | `4b` `5b` |

**规则（照这个来，别自己定）**：
- **数字永远是「离根几步」**，与走哪条支无关 —— 所以主线上它就等于手号。
- **后缀 = 从这一手往上找，第一个「岔口祖先」**（该祖先满足 `_cs.length > 1` 且自己不是它的 `_cs[0]`），
  自己在那个 `_cs` 里的下标 1→`a`、2→`b`、3→`c`…
- **同一支上所有手共用同一个后缀** —— 它们往上找到的是同一个岔口，天然如此。

**① 加纯函数**（放「手数分支」那一节）：

```js
/* 一个节点的显示名 —— 决策 6 的「12a 式」。
   纯函数（只吃 node），所以能在探针里直接单测、不受界面状态影响。 */
function moveLabelOf(node) {
  if (!node) return '';
  let depth = 0, suffix = '';
  let cur = node;
  while (cur && cur._p) {
    depth++;
    const p = cur._p;
    /* 只认「自己不是主变那条」的岔口；从下往上走，**第一个**遇到的岔口就是最近的 */
    if (!p._virtual && p._cs && p._cs.length > 1) {
      const i = p._cs.indexOf(cur);
      if (i > 0 && !suffix) suffix = String.fromCharCode(96 + Math.min(i, 26));
    }
    cur = p;
  }
  return String(depth) + suffix;
}
```

27. **`restoreAnalysisForPath` 的循环上界写错了**：`i < state.moves.length` 应为 `<=`。

    ——表现为「切回旧线后，**最后一手**的胜率/目差/精度回不来」（⑦2/⑦3/⑦4 三条 FAIL 同时指向它）。

28. **探针里的坐标换算必须走 `GTP_COLS`，不能用 `charCodeAt - 65`**。
    围棋 GTP 坐标**跳过 I**（A B C D E F G H **J** K L…），`'K'.charCodeAt(0) - 65 = 10`
    而 K 其实是 9、`'Q'-65 = 16` 而 Q 其实是 15 → 探针自己把 K10 当成 L10，
    **一口气错 4 条断言（②1/②2/④/⑥2），程序全对**。同理：断言里手写的 SGF 坐标
    （`W[qd]` / `W[qp]`）也是照错口径写的，实际应为 `W[pd]` / `W[pp]`。
    **写死坐标前先用程序自己的 `SGF_COLS`/`GTP_COLS` 算一遍。**

### ★★★ 讲解那条的真根因（找了好几轮，值一记）

**不是坐标系。** 先怀疑过上下颠倒，专门做了实验：给模型单颗子问"它下在哪"，
放 D16 答 D16、放 Q16 答「右上角」、放 C4 答「左下角」—— **全对**。

**真根因**：盘面给的是 `boardAt(at-1)` —— **这一手之前**的局面。
在那个局面上**正好轮到刚落子的那一方走**，模型看到"该我选点了"，
于是退回它最擅长的"列候选点"。D4 就是它列的候选之一。

对照实验（同一真实局面各跑 3 次）：

| 传给模型的盘面 | 它讲出的坐标 | 判定 |
|---|---|---|
| **这一手之前**（原状） | `D4 C3 D3 D13 C14 F15` | ❌ 全是**盘上没有**的点 |
| **含这一手**（改后） | `C16 E17 D14` | ✅ 全是盘上**真实有**的子 |

### ★★ 这一程的踩坑表（讲解部分，全是实测抓的）

1. **预填句必须放在最后，要求写在它前面**
   原来是「预填句 \n（要求）」，模型会**接着那段括号要求往下写** —— 实测吐出
   「…下出来，现在轮到白棋第6手，你是白棋，我让你下棋，你下出来，我来分析。）」
   整段是要求形态的文字，根本不是讲解。**预填的定义就是"模型从这儿继续写"**。

2. **好坏结论不能交给模型判断**
   同一手亏 8.5% 的棋跑两次：一次骂「不太像棋啊」，一次夸「碰得很有想法」。
   改法：结论句由 `verdictLead()` **由程序**写进预填（好坏本来就该由 KataGo 定），
   模型只负责顺着补理由。

3. **结论句也不能是硬模板**（首相看出来的）
   第一版用「这手棋下得不好 —— 」，217 手全长一个样、一眼假。
   改成 `LEAD_POOL`：每种判定 3~5 种口语说法、**按手数轮换**（不用随机数，好复现）。

4. **`trimCoachTail` 的 `if (m1 > 0)` 漏了位置 0**
   正文**一开头**就是「现在轮到白棋第6手…」时 `m1 === 0`，不砍 → 整段垃圾留着。

5. **成对的括号清理必须排在"去掉开头括号"之前**
   顺序写反 → 开头的「（」先被吃掉，成对匹配的正则再也匹配不上，
   只剩一个孤零零的「对着棋盘沉思片刻）」。

6. **清理判据要跟着模型的"换皮"走**
   实测抓到：`我来分析几种可能的应对` → `我有几个不错的应对选择` →
   `现在白棋有几个不错的选点值得考虑`。每补一轮，它就换一种说法。

7. **`cleanCoachText` 里清百分比是安全的**
   程序写的第二段对照句（`bestPointNote`）是在 `coachTextReady` **之后**才拼的，
   不会被误伤 —— 所以模型自己编的「胜率71.4%」可以放心整句删掉。

8. **`maxTokens` 太小会把生成截断**（用户看出来的第二轮问题）
   原来每手只给 340 —— 实测模型写到 460 字左右就被掐掉，结尾是
   「这个变化虽然也能吃掉黑」这种半句；更糟的是**短输出也被放行**，
   于是有些手只剩「这手不行，这手有问题啊。」一句结论、**没有任何理由**
   （首相原话：「这跟直接列个胜率有啥区别呢」）。
   改：maxTokens 340 → **520**；`coachUsable` 门槛 40 → **70 字**。

9. **`trimCoachTail` 会把「过渡句」误当支招**
   「让我仔细看看这个局部的棋形。」本身零信息量，但它后面跟的往往是**真正的理由**。
   从它那儿砍，正文只剩 7 个字 → 被判太短 → 白跑一次重试。
   改：过渡句交给 `cleanCoachText` **只抹掉句子本身**，后面的内容留着。

10. **判据要跟着模型的"换皮"走**（第三轮）
    实测抓到：`我来分析几种可能的应对` → `我有几个不错的应对选择` →
    `现在白棋有几个不错的选点值得考虑` → `白棋现在有几个主要选择`。
    最后这个是「白棋」和「有几个」中间插了个「现在」，老判据就漏了。

11. **动作旁白词表也要长**（第三轮）
    抓到的第二拨：「（突然坐直身体）」「（摸着下巴思考）」「（自信地拍扇子）」
    「（补充说明…）」。另外模型会在 `</reasoning>` **之后**再补半句然后被停词截断 ——
    现在 `</reasoning>` 后面的内容一律砍掉（**必须先砍再删标签**，顺序反了就找不到标记）。

12. **棋谱库的「带讲解」标记不能只看文件在不在**
    用户实测：「棋谱库显示带讲解，打开却是空的」—— 其实是讲解被新版本作废了。
    改：`records:list` 只读 `.coach.json` **开头 400 字节**取顶层 `cv`（新增，
    `saveCoachFile` 会把它写到 JSON 顶层），渲染进程跟自己的 `COACH_VER` 比：
    一致标「带讲解」，旧了标「**讲解要重讲**」。

13. **PowerShell 里调外部程序必须写 `&`**
    `"C:\...\node.exe" --check main.js` 会被当成字符串 → ParserError →
    **整条命令从那一行起全都不执行**（连后面的"杀进程 + 重启"都没跑）。
    当时的表象极具迷惑性：看着像"改了没生效"，实际是新代码根本没加载。
    这次是靠"验证脚本读到的还是旧行为"才反应过来的 —— **改完一定要确认真重启了**。

14. **★ 逐手过目 172 手之后汇总出来的「6 类脏话」**（第三轮清理，全部有真实原句）
    跑完 217 手逐手看，模型翻来覆去就这几种毛病：

    | # | 症状 | 真实原句 | 修法 |
    |---|---|---|---|
    | 1 | **数字分点罗列**（替对方列应手） | 「1. 白棋下在J18粘住」 | `trimCoachTail` 的 m2 加 `\n\s*[1-9][.、]` |
    | 2 | 「我建议…」 | 「我建议黑棋立即在B17扳一手」 | m1 加 `我建议\|建议(黑棋\|白棋)` |
    | 3 | 「X棋现在可以下在…」 | 「白棋现在可以下在P5粘住」 | m1 加词 |

    | 5 | 动作旁白**第三拨** | 「（自言自语：…）」「（用教学语气）」 | 词表再加长 |
    | 6 | 「我仔细计算了一下…」 | 「这手棋有三个重要作用：1. …」 | m1 加 `我仔细计算\|我仔细推演` |

    > 第一轮补「我来分析」，第二轮补「我有几个不错的应对选择」，
    > 第三轮补「白棋**现在**有几个」「**1. 2. 3.**」。**它总会换个说法再来。**

15. **记谱清理不能整个删，只能去前缀**
    原来是 `.replace(/[XO]-[A-T]\d{1,2}/g, ' ')` —— 把 `X-L17` 整个抹成空格。实测后果：
    「黑棋在 X-L17 一带」→「黑棋在  一带」（悬空的"一带"）；
    「X-L1 7一带」→「**7一带**」（**用户截图报的这个**）。
    现在只去前缀：「X-L17」→「L17」。
    **用户当初抱怨的只是"一个字母加横杠接坐标"这个格式看不懂，坐标本身是该留的。**

16. **还是修不掉的（已知，先留着，别当成新 bug 去查）**
    · **「首先，…」后面接不上** —— 模型写了"首先"却没有"其次"，但句子本身是完整的，
      自动砍会误伤正常讲解。真要治得从 prompt 里禁掉"首先/其次"这类词。

    · **模型缺字/错字**（第 48 手把「白棋现在下R9碰」写成「棋现在下R9碰」）

    `coachVerOK` 判定"都讲过" → **一手没重讲**。
    那 4.5 分钟里只干了：KataGo 算一遍 + 把**旧讲解**从文件读回来。

    > **规矩：动了 prompt / 清理判据 / 讲解结构，必须同时把 `COACH_VER` 加一。**
    > 已经给 `dev/_cdp_batch217.mjs` 加了防呆：点完「全盘讲解」立刻打印
    > 「起步时已有 N 手讲解」；N 接近 217 就报警并提示检查 `COACH_VER`。

18. **★★★ 最严重的一类：模型编盘面**（首相实测，2026-10-13）
    第 8 手 D3 落在**空空如也的左下角**，讲解却写：
    「白棋这手**碰**得有点早」「黑棋在**四个角**都有子力，白棋的布局明显落后了」——
    **全是编的**。黑棋右下角一颗子都没有，D3 也没"碰"任何东西。

    **根因**：我们让 7B 自己读那个 19×19 数字矩阵判断"碰到了谁"。
    它读不准，读不准就凭"棋局感"瞎编。

    **改法：盘面事实全部由程序算好喂进去**，模型只负责顺着事实讲道理（那正是它擅长的）：
      · `touchFacts()` —— 这一手挨着谁；**四周八格没子就明说「它既不是碰、也没挨着谁」**
      · `cornerFacts()` —— 四个角（各 4×4）里黑白各几颗
      · `posKind()` —— 这一手是什么位置（星位 4-4 / 小目 3-4 / 三三 3-3 / 边 / 中腹）
        —— 实测模型把 D3 这个 3-4 说成「**星位**」

19. **★★ 提示词的三条排版规矩**（都是实测撞出来的，代码里写在 `coachPromptActual` 上方）
    ① **要求写在前面、预填句放最后** —— 反过来模型会接着"要求"往下写，
       吐出「…下出来，现在轮到白棋第6手，你是白棋，我让你下棋…」；
    ② **事实紧贴预填句** —— 离得越近越管用。放最前面时，它照样开口就写"碰"；
    ③ **「空的就不许写碰」要写成一条独立规矩** —— 只塞在事实里那句「它不是碰」，
       它照样无视。

    同一手、同一局面，改前改后对比：
      · 改前：「白棋这手 **D3 碰**，明显是针对黑棋在左上小目的布局」
      · 改后：「白棋在**左下小目（3-4）落子**，这个位置太偏了，既不能有效占角……黑棋完全可以不理它」

20. **7B 的能力边界（治不好的，别再花时间）**
    · **细粒度幻觉**：事实里写了「左上 黑1白2」，它照样说「黑棋左上**两子**」。
      除非把每个角的每一颗子都列进 prompt（不现实），否则治不了。
    · 会编"金句"（「神之一手」）、会缺字、会车轱辘把话再说一遍。

    > **结论（以后按这个分工）**：**事实类**的东西（坐标、胜负、目损、碰到谁、什么位置）
    > 一律**由程序给**，一个字都不许模型猜；
    > **棋理类**的分析（为什么好/不好）交给模型，但别指望它精确。

## 零之二、引擎自动挑对显卡 + 双引擎懒人包（2026-10-09）

**起因**：用户发现懒人包里**只有 N 卡（CUDA）引擎**，A 卡 / Intel 用户下完 8.5 GB
才发现引擎起不来；而且说明文件一个字没提显卡。

**做了什么**：

| 改动 | 文件 |
|---|---|
| **软件自动挑对引擎** —— 两套引擎并存时按本机显卡挑；配好的那套不匹配就自动换另一套 | `main.js` `pickWorkingEngine()` / `pickKataGoEngineDir()` / `pickLoGosDir()` |
| **自检同时查两套引擎** —— 原来只查 KataGo；A 卡用户换完 KataGo 仍用不了 LoGos 却没人说 | `main.js` `probeLlamaDevices()`（跑 `llama-server --list-devices`）、`renderer/app.js` `renderEngineCheck()` |
| **GPU 探测改同步版** —— `defaultPaths()` 在模块加载时同步跑，用不了 async 的 `gpuInfo()` | `main.js` `detectGpuBrandSync()`（PowerShell CIM，带缓存） |
| **懒人包带两套引擎** —— `KataGo\engine`(CUDA) + `KataGo\engine-generic`(OpenCL)、`LoGos\`(根目录 CUDA) + `LoGos\runtime-generic`(Vulkan) | 懒人包 |
| **使用说明重写** —— 说明显卡自动挑、怎么用软件内自检 | `懒人包使用说明.txt`（源头移到仓库根目录） |
| **README 补一句** —— 懒人包用户不用管引擎那节 | `README.md` §显卡品牌 |

**★ 踩过的坑（都写进代码注释了）**：
1. **`(?m)` 不是 JS 的正则内联标志** —— 写了直接 `SyntaxError`。JS 用 `/re/m`。
2. **`pickWorkingEngine` 里 `base` 多推了一层** —— `have` 已是引擎目录，再 `dirname` 就跑到程序上级，
   于是永远找不到另一套、**静默不换**。这个 bug 是在"要砍掉独立自检器"之前专门去测才发现的。
3. **`.ps1` 必须带 UTF-8 BOM** —— 缺了 PowerShell 5.1 按 GBK 读，报**18 个假语法错误**。
   `edit` 工具每次改完都会去掉 BOM，**改完必须补**（用 `dev\_check_encodings.ps1` 查）。
4. **`param()` 必须是注释后的第一条语句** —— 放到中间会被当普通语句**忽略**，
   传进去的参数静默失效（排查时极其迷惑）。
5. **别用命令行传带反斜杠的路径** —— `"D:\GoStudy\_t2"` 里的 `\t` 会被 PowerShell 当 **Tab 转义**。

**★ 砍掉的东西**：一个独立的 `本机运行环境自检.bat/.ps1`。
用户在"软件内已有自检 + 自动挑引擎"之后判断它是多余的 —— 而且那个脚本我连踩 6 个坑
（`ReadKey` 在无控制台时**永久阻塞**、递归删 2 GB 碎文件要几分钟、跨盘移动退化成真拷贝……），
根因是**这个环境里没法真正测 .bat/.ps1**。撤掉是对的。

**★ 未验证（诚实记录）**：**A 卡 / Intel 显卡的分支没有实机验证过**（开发机只有 RTX 4070）。
KataGo 的 OpenCL/Vulkan 引擎能加载、能自报后端（已实测），但真在 A 卡上跑没测过。

## 零之三、文档里的"断言式说法"必须实测（2026-10-09 立的规矩）

**起因**：用户随口问了一句"解压成嵌套两层能用吗"，我去测 —— 结果发现说明文件里
那句**「别解压成嵌套两层，程序按上一级找引擎」是错的**（打包版按 exe 所在目录找，
跟嵌套无关）。于是把 README / 英文 README / 软件内帮助 / 使用说明**所有断言式说法
逐条实测了一遍**，又查出两处同类错话。

### ★★ 发现了一个**反复出现**的错法：把"源码模式"的行为当成"打包版"的行为

| 文档里的错话 | 真相 |
|---|---|
| 「别解压成嵌套两层 —— 程序按**上一级**找引擎」 | 打包版按 **exe 所在目录**找；「上一级」是源码模式 |
| FAQ「找不到引擎？默认约定是放在项目**上一级**」 | 同上（同一个病） |
| 「纯 CPU 模式（**设置面板里能改**）」 | 设置面板**没有**任何切换后端的控件；要下 `eigen` 版再指路径 |

**为什么会这样**：这些说法多半写在"只有源码模式"的时期，后来加了打包版却没回头改。

都要按"打包版怎么走、源码模式怎么走"分别核对一遍。

## 四、动手前必读的三条纪律（都是今晚踩出来的）

1. **.bat 文件必须 UTF-8 带 BOM + CRLF**，否则 cmd 会把中文当命令、
   把 `echo` 拆成 `ho`（实测无 BOM → 4 条报错，带 BOM → 0 条）。
   `_deploy.sh` 里有检查，别绕过它。
2. **测试的判据和被验的东西一样容易错**。今晚有三次"测试报了 ★，其实是判据写错了"
   （拿 GBK 字节比 UTF-8 文本、用"抹掉所有 C[] 再比"证明"没动别处"、颜色大小写）。
   **判据写错会掩盖真 bug，也会造出假 bug** —— 两者都很贵。
3. **视觉改动必须量真实几何**，不能只查 `hidden === false`。
   今晚"提示浮层盖在棋盘正中间"就是这样被"✓ 通过"放过去的，
   最后靠截图 + `getBoundingClientRect` 才发现。

# 2026-10-14 深夜：树布局「线贴到珠子」——根因查清并修复

## 一、根因：`findRow` 的兜底在「明知穿珠」的情况下硬塞

`branchFits` 的三条判据（① 格子不冲突 / ② 入线不碰已放置的珠子 / ③ 已有斜线不碰本支珠子）
本身没错。问题在 `findRow` 的最后一行 **`return treeLanes;`** —— 循环把 `from..treeLanes`
全试过、**全不通过**，却仍然把这条支塞回行尾。

诊断实测（真实棋谱 181 手，一轮布局放 14 条支）：

```
兜底触发 3 次，每一次都发生在「只试了 1 行」之后
  · 父 第5手(行0) 支首 第6手 → 硬塞 行3  起始候选 行3  试了 1 行全不通过
  · 父 第4手(行0) 支首 第5手 → 硬塞 行5  起始候选 行5  试了 1 行全不通过
  · 父 第4手(行0) 支首 第5手 → 硬塞 行6  起始候选 行6  试了 1 行全不通过
重放判据②：这 3 次「放置当时」就该被拦住
  · 第5手(行0)→第6手(行3)  撞 1 颗，最近 11.1px
  · 第4手(行0)→第5手(行5)  撞 1 颗，最近 6.7px   ← 与首相报的过近明细逐位吻合
  · 第4手(行0)→第5手(行6)  撞 2 颗，最近 5.6px   ← 同上
```

「只试了 1 行」的原因：`nextFree` 把起始行推到了行尾，循环里根本没有第二行可试。

## 二、几何铁律（★ 以后改 `TREE_W` / `TREE_H` 前必看）

同一父第 k 条支的入线，到「紧邻上一个兄弟」珠心的距离 = **`A·H / √(A² + k²H²)`**
（A = `TREE_W` 列距，H = `TREE_H` 行距）

| 列距 A | k=1 | k=2 | k=3 | k=4 | k=5 | k=6 |
|---|---|---|---|---|---|---|
| 旧 **34** | 28.5 ✓ | 16.2 ✓ | **11.07 ✗** | 8.4 ✗ | 6.74 ✗（实测 6.7） | 5.64 ✗（实测 5.6） |
| 新 **40** | 31.7 ✓ | 18.7 ✓ | **12.9 ✓** | 9.8 ✗ | 7.91 ✗（实测 7.9） | 6.61 ✗（实测 6.6） |

**结论**：
- 旧列距只有 **k ≤ 2** 安全；新列距 **k ≤ 3** 安全。
- ⚠️ **加大行距 H 救不了** —— 距离的上界是 `A/k`，H 越大反而越贴近这个上界。要治只能加列距 A。
- 要救 k=4 需 **A ≥ 47.2**、k=5 需 **A ≥ 59**、k=6 需 **A ≥ 72**（树宽翻倍，不划算）。
- ⇒ **k ≥ 4 是几何无解区间，别再去"修"它**（公式摆着，改行高/列宽都是白费）。

## 三、改了什么（`renderer/app.js`）

2. **`TREE_W` 34 → 40**（列距 +18%，把 k=3 从"差 0.4px"抬进安全区）。

## 二、备份机制整改（首相：「一个完整备份包 8G，太浪费」）

**根因**：`dev/_sync_deploy.ps1` 第 63 行起的"可回退备份"是 `robocopy /E` **全量**。
引擎自 2026-10-09 搬进免解压版内部之后，`KataGo\`（2.3 GB）+ `LoGos\`（5.6 GB）
被一起复制 —— 每份从注释里写的 368 MB 涨到 **8259 MB**，留 2 份 = 16.5 GB。

**改法**：`robocopy` 加 `/XD $noBakDirs`，排除 `KataGo`、`LoGos`。**安全**，三条理由：
① 同步流程本来就不动它们（`$keep` 里保着）；② 回退时它们原样躺在 `$DeployDir` 里，
不需要从备份恢复；③ 引擎内容基本不变，真要留底留一份就够。
**结果**：每份 **8259 MB → 约 376 MB**（省 95%）。备份后还会打印实际体积，一眼看得见。

## 三、★ 坑位 48：`edit` 工具会剥掉 UTF-8 BOM

用 edit 改过 `dev/_sync_deploy.ps1` 和 `dev/_update_lazy.ps1` 之后，**BOM 没了** ——
这两个文件含中文，PS 5.1 会按 GBK 解析而**语法崩**。项目自带的 `_check_encodings.ps1` 直接报红。

- **判据**：`.ps1` **必须带 BOM**；**行尾不卡**（`_paths.ps1` 是全 LF 也判通过）——
  只有 `.bat` 才必须 CRLF。
- **补法**（PowerShell）：
  ```powershell
  $b = [IO.File]::ReadAllBytes($f)
  if (-not ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)) {
      [IO.File]::WriteAllBytes($f, ([byte[]](0xEF,0xBB,0xBF)) + $b)
  }
  ```
- **规矩：改完任何 `.ps1` / `.bat`，跑一次 `dev/_check_encodings.ps1` 复核。**
